# 主服务器与专用执行节点部署设计

## 1. 文档目标

本文档定义如何将当前双机同构的现货机会扫描与消费部署，演进为更符合生产目标的两层结构：

- 主服务器负责公共扫描、Redis、中央信号分发
- 专用执行节点只负责指定用户的下单执行
- 特定用户的私有交易流量固定走专用节点的公网出口或代理出口

本文档只覆盖当前项目已有 `scanner -> Redis -> consumer/probe` 运行链路的部署重构，不重写总套利系统，也不扩展新的交易策略。

## 2. 背景与现状

当前运行时已经具备以下能力：

- [worker_service.py](file:///d:/old/FuRunSystemV4/app/runtime/worker_service.py) 支持 `scanner` 与 `consumer` 两种角色启动
- [live_spot_flow.py](file:///d:/old/FuRunSystemV4/app/runtime/live_spot_flow.py) 负责扫描机会并写入 `stream:spot_opps`
- [live_workers.py](file:///d:/old/FuRunSystemV4/app/runtime/live_workers.py) 中的 `RedisSpotConsumer` 负责读取 `stream:spot_opps`
- 两台远端测试机当前都能运行同一套 `scanner + consumer` 服务
- 当前 `.env.worker` 与 `systemd` unit 只有 `worker_role`、`worker_region` 两类基础角色信息

当前缺口不在扫描或下单核心逻辑，而在节点职责与任务路由：

- 两台机器仍是双机同构测试态
- 专用 IP 节点还不能只承载指定用户的执行流量
- Redis 中还没有节点级执行任务流
- 运行配置还没有“主服务器 / 执行节点 / 用户绑定节点”的明确建模

## 3. 问题定义

如果继续维持双机同构，会有以下问题：

1. 专用节点仍会承担扫描或公共消费职责，浪费专用出口
2. 无法保证某个用户的交易请求稳定走同一节点
3. 后续扩到多用户、多专用节点时，任务路由边界会迅速混乱
4. 运维层无法明确区分“主控故障”与“执行节点故障”

用户当前明确目标是：

- 一台作为主服务器
- 一台作为交易下单时特定用户的专用 IP 节点

因此第二台机器必须被设计为纯执行节点，而不是继续直接参与公共机会扫描。

## 4. 设计目标

本次设计满足以下目标：

1. 主服务器与专用执行节点职责清晰拆分
2. 执行节点不再直接参与公共扫描
3. 指定用户可稳定路由到指定执行节点
4. 现有 `scanner -> Redis -> probe` 链路可渐进迁移，不要求推翻已有代码
5. 当前双机测试环境可以平滑从同构态过渡到目标态

## 5. 非目标

本次不做以下内容：

- 不重写总设计文档中的全平台分层架构
- 不引入数据库版任务编排中心
- 不一次性实现多节点租约抢占与自动接管
- 不解决 `bitget` 测试网业务错误
- 不把执行节点升级为完整多用户多交易所生产集群

## 6. 方案比较

### 6.1 方案 A：主服务器集中调度，执行节点纯执行

做法：

- 主服务器运行 `scanner`，负责公共机会发现
- 主服务器新增一个路由层，把公共机会转换为用户级执行任务
- 专用执行节点只消费发给自己的执行任务流

优点：

- 最符合“专用 IP 只给指定用户下单”的原始目标
- 公共流量与私有交易流量彻底拆开
- 后续扩展为多执行节点时边界最清晰

缺点：

- 需要新增一层节点级任务流和基础路由配置

### 6.2 方案 B：执行节点直接消费公共机会流

做法：

- 主服务器继续扫描并写 `stream:spot_opps`
- 执行节点自己订阅公共机会流，再按用户或交易所过滤

优点：

- 当前改动较小

缺点：

- 执行节点仍暴露在全局机会流上
- 过滤逻辑分散到执行节点，不利于统一治理
- 更容易出现重复消费和边界漂移

### 6.3 方案 C：继续双机同构，只做配置软区分

做法：

- 两台机器继续保留 `scanner + consumer`
- 仅通过环境变量约束哪台机器主要处理哪类任务

优点：

- 改动最小

缺点：

- 与目标形态偏差最大
- 长期会阻碍用户路由、节点扩容和专用出口隔离

## 7. 推荐方案

推荐采用 `方案 A：主服务器集中调度，执行节点纯执行`。

选择原因：

- 与用户当前“主服务器 + 特定用户专用 IP 节点”的诉求完全一致
- 与总设计文档中“任务路由到所属 worker、私有交易会话隔离”的原则一致
- 能最大限度复用现有 `scanner`、`consumer`、`probe` 代码，而不是重新造一整套运行模型

## 8. 目标运行架构

### 8.1 节点角色

系统拆成三类运行角色：

1. `scanner`
2. `dispatcher`
3. `executor`

其中：

- 主服务器运行 `scanner + dispatcher`
- 专用执行节点运行 `executor`

### 8.2 角色职责

#### `scanner`

负责：

- 拉取交易所 orderbook
- 计算最佳现货机会
- 写入公共 Redis 排行和公共机会流

不负责：

- 不直接决定哪个用户要执行
- 不直接承担专用节点下单职责

#### `dispatcher`

负责：

- 读取公共机会流
- 根据用户绑定关系决定任务去向
- 将公共机会转为节点级执行任务
- 过滤不属于本节点的用户

不负责：

- 不执行下单
- 不持有用户专属私有交易连接

#### `executor`

负责：

- 只消费分配给本节点的执行任务
- 装配本节点允许处理的用户凭证与代理
- 调用现有 `SpotArbitrageProbeService` 或后续正式执行服务完成下单链路

不负责：

- 不扫描公共机会
- 不消费全局公共机会流

## 9. Redis 数据流设计

### 9.1 保留的公共流

继续保留当前公共机会流：

- `stream:spot_opps`

用途：

- 只作为“公共扫描结果流”
- 不再由专用执行节点直接消费

### 9.2 新增的节点级执行任务流

新增节点级执行任务流：

- `stream:spot_exec_tasks:<node_id>`

示例：

- `stream:spot_exec_tasks:main`
- `stream:spot_exec_tasks:node-a`

用途：

- 主服务器将某个用户的执行任务写入其绑定节点的专属流
- 执行节点只读自己的专属流

### 9.3 新增执行结果流

建议新增：

- `stream:spot_exec_results`

用途：

- 执行节点回写成功、失败、异常、风控拒绝等结果
- 主服务器后续可基于该流做审计、通知和恢复

### 9.4 路由缓存键

建议新增或正式启用以下 Redis 键：

- `route:user_node:{user_id}`
- `health:node:{node_id}`

其中：

- `route:user_node:{user_id}` 保存用户当前绑定的执行节点
- `health:node:{node_id}` 保存节点心跳、版本、角色和最近错误状态

## 10. 配置模型设计

### 10.1 Worker 角色扩展

当前 `worker_role` 只有：

- `scanner`
- `consumer`

建议扩展为：

- `scanner`
- `dispatcher`
- `executor`

兼容原则：

- 现有 `consumer` 在迁移期可作为 `dispatcher + executor` 的兼容角色保留
- 最终目标是不再让专用节点运行老式公共 `consumer`

### 10.2 新增节点配置

建议在 `WorkerSettings` 中新增以下字段：

- `node_id`
- `node_role`
- `executor_enabled`
- `dispatch_source_stream`
- `executor_stream_key`

语义建议：

- `node_id`：节点唯一标识，例如 `main`、`node-a`
- `node_role`：节点类型，例如 `primary`、`dedicated_executor`
- `dispatch_source_stream`：默认 `stream:spot_opps`
- `executor_stream_key`：例如 `stream:spot_exec_tasks:node-a`

### 10.3 用户绑定配置来源

首版建议采用“静态配置优先，数据库路由后补”的策略。

首版可接受的绑定来源：

1. 本地配置文件
2. 环境变量映射
3. Redis 路由键

推荐首版使用：

- Redis 路由键作为运行时读取源
- 本地初始化脚本负责写入测试用户与节点绑定关系

原因：

- 不需要先引入数据库模型改造
- 更贴合当前已有 Redis 驱动运行模式
- 便于远端测试环境快速切换用户归属

## 11. 运行时改造设计

### 11.1 主服务器

主服务器的运行职责调整为：

- `scanner` 持续写 `stream:spot_opps`
- `dispatcher` 持续读取 `stream:spot_opps`
- `dispatcher` 根据 `route:user_node:{user_id}` 决定是否为该用户创建执行任务
- 若用户命中专用节点，则写入对应 `stream:spot_exec_tasks:<node_id>`

### 11.2 专用执行节点

专用执行节点的运行职责调整为：

- 只运行 `executor`
- 只读取自己的 `stream:spot_exec_tasks:<node_id>`
- 加载仅本节点允许处理的交易所凭证、代理和用户路由

### 11.3 现有 consumer 的迁移方式

当前 `RedisSpotConsumer` 是直接读取 `stream:spot_opps` 后立即调用 dispatcher/probe。

迁移建议分两步：

1. 先新增一个“节点级任务消费者”，保持现有公共 `consumer` 不动
2. 验证节点级任务流稳定后，再逐步把专用节点从公共 `consumer` 中摘除

这样可以避免一次性替换所有消费链路。

## 12. systemd 设计

### 12.1 主服务器 unit

主服务器建议运行：

- `furun-spot-scanner.service`
- `furun-spot-dispatcher.service`

### 12.2 专用执行节点 unit

专用执行节点建议运行：

- `furun-spot-executor.service`

### 12.3 迁移期兼容策略

迁移初期允许：

- 主服务器继续保留旧 `consumer` 用于联调
- 专用节点关闭旧 `scanner`
- 专用节点最终只保留 `executor`

这样可以把当前双机同构平滑迁移为目标形态，而不是一次性切断。

## 13. 错误处理与恢复

### 13.1 主服务器故障

主服务器故障时：

- 专用执行节点应停止接收新任务
- 已收到的任务继续尽量完成或安全退出
- 不允许执行节点自行回退到扫描公共机会

### 13.2 执行节点故障

执行节点故障时：

- 主服务器继续扫描公共机会
- 发往该节点的新任务可暂存于其任务流
- 首版不做自动改派到其他节点，避免专用 IP 语义漂移

### 13.3 幂等要求

以下动作必须具备幂等或近幂等能力：

- 同一执行任务重复写入节点流
- 执行节点重启后重复读取未确认任务
- 执行结果重复回写结果流

首版可以通过执行任务中的 `task_id` 或 `idempotency_key` 做基础去重。

## 14. 安全与隔离要求

### 14.1 节点权限边界

专用执行节点只应持有：

- 本节点负责用户所需的交易所凭证
- 本节点对应的代理配置

不应持有：

- 全量用户凭证
- 与本节点无关的专用代理配置

### 14.2 出口隔离原则

- 扫描流量与私有交易流量分机承载
- 专用节点上的私有下单请求固定走该节点公网 IP 或其账户绑定代理
- 不允许为了方便临时把该用户任务回退到主服务器直连执行，除非管理员明确变更路由

## 15. 迁移计划

推荐按以下阶段迁移：

1. 保持当前双机同构，先补文档与配置模型
2. 新增 `dispatcher` 与 `executor` 角色定义
3. 在主服务器增加节点级任务下发能力
4. 在专用节点增加节点级任务消费能力
5. 验证专用节点可独立执行绑定用户任务
6. 停掉专用节点上的旧 `scanner` 和旧公共 `consumer`

## 16. 验收标准

完成后至少满足以下标准：

1. 主服务器只承担公共扫描与任务分发
2. 专用执行节点不再直接扫描公共机会
3. 指定用户的任务只进入其绑定节点的执行任务流
4. 专用节点只消费自己的 `stream:spot_exec_tasks:<node_id>`
5. 专用节点执行结果可回写到统一结果流
6. 主服务器故障不会让执行节点擅自转为公共扫描模式
7. 当前 OKX 资源释放修复不因节点拆分而回退

## 17. 结论

当前双机部署只是联调用的同构测试态，不是最终目标形态。后续应收敛到“主服务器负责公共扫描和中央调度，专用执行节点只负责绑定用户执行任务”的结构。

该方案既符合总设计文档中的任务路由与私有交易隔离原则，也能最大化复用当前已经跑通的 `scanner`、`Redis`、`probe` 和 `systemd` 资产，为后续多用户、多节点和专用 IP 扩展打下清晰边界。
